# 技术博客写作 (Tech Blog Writing)

写给不看源码的人读懂的原理文章：讲明白机制为什么这样，不堆术语、不贴实现。语言规则交给 `humanize-writing`。

## 底线
- 不假设前置知识，行话必须能被上下文解释。
- 原理优先于实现：先讲问题出在哪、为什么要这个方案。
- 只写站得住的事实，有判断、讲取舍（为什么选它、代价是什么、何时别用）。
- 代码、配置项、API 字段、报错原文属于事实，逐字保留不改写。

## 结构
1. 问题钩子：一个具体场景，不做会怎样。
2. 一句话结论。
3. 机制拆解：按因果链展开，因为 X 导致 Y，所以要 Z。
4. 边界与代价。
5. 收尾：讲完直接结束，或写下步要解决的问题。

缺项就跳过，不为凑结构硬写。

## 讲懂机制
- 术语首次出现给一句话解释：是什么、为什么需要它，之后不再重复定义。
- 一次只引入一个新概念，它依赖的旧概念先讲完。
- 抽象概念必须有锚点：落到数字、真实场景或类比。“开销很大”改为“多一次内存拷贝，p99 从 40ms 涨到 180ms”。
- 类比只用于搭桥，用完补一句它哪里不严谨。
- 并列超过三项就合并或改写成因果链。

## 配图
- 架构图、流程图必须是渲染好的 PNG/SVG 图片文件；ASCII 字符画和 Mermaid、PlantUML、Graphviz 源码不算图。
- 出不了图就用文字讲清组件关系和数据流向，不硬凑伪图。
- 每张图配一句它说明什么，图里画过的内容正文不复述。
- 讲数据流、状态变化、调用关系的图，优先于只列模块的框图。

## 代码区块
代码前一句话说明这段解决什么，代码后说明关键行为。正文讲原理时只引用片段或行号，不整段贴实现。

## 自检
术语都有解释；抽象表述都有锚点；图是真实图片文件；代码与原文逐字一致；无凑结构段落；语言层已过 `humanize-writing` 自检。

用户指定读者为同行专家或内部文档时，可省略术语解释与类比，其余规则仍适用。
